# 接入管理与 AI 授权

管理入口：`https://pay.bornforthis.cn/admin`。管理员登录后，可以查看经营概览和订单、手动关闭或重新启用订单、核实补记付款、维护平台、生成 AI 接入任务及撤销短期授权。这里的“平台”和支付 API 中的产品 `clientId` 是同一个隔离单位。

支付宝应用已上线，2026-10-15 已完成 `xhs-downloader` 一笔 ¥3.00 日付的正式付款、通知送达和实际后端会员开通验收；临时验收关闭后，用户明确授权正式开放，正式配置为 `PAYMENT_ENABLED=true`。实时状态以健康接口或签名目录的 `acceptingPayments` 为准；其他套餐、客户端、手机渠道及退款未据此标记通过。注册平台、生成任务或保存商品不代表该产品已经完成付款与权益验收。

## 一键交给产品开发 AI

1. 登录 `/admin`，为新平台填写固定 `clientId`，或从已有平台选择“生成更新任务”。
2. 选择域名模式。**自动发现**允许 AI 为该产品增加必要公网 HTTPS 来源，可先填产品网址作线索，也可留空；新增来源出现在计划与应用后的后台记录。**固定范围**要求填写允许的来源，每行一个，例如 `https://xhs.download.brclio.com`。来源不包含路径；确有需要才授权 `https://*.brclio.com`，该形式不包含根域名。
3. 选择套餐来源。**读取项目现有套餐**让 AI 先从后端商品配置、已有只读权限的套餐记录及定价文档取证，并与前端交叉核对；不必再人工抄一遍价格。**人工指定**使用你在项目会话提供的商品、价格、权益及有效期。两种模式遇到缺失或冲突都应询问你，不编造收费规则。
4. 点击“生成并复制 AI 接入任务”。任务包含完整通用 Skill、目标平台、模式、到期时间，以及最长 2 小时的临时接入令牌。把完整任务交给负责该产品后端的 AI 即可，不需要额外附 ZIP。
5. AI 先检查原产品登录、订单、权益和已有支付代码，再读取授权 context、生成变更计划、核对前后差异并应用。AI 对产品仓库的访问、编辑和部署仍需来自当前用户任务授权。
6. 完成后查看平台配置、版本和授权状态；必要时撤销未到期授权。

复制任务属于敏感内容，其中的短期令牌允许读取**该平台**的接入凭证并执行指定新增或更新操作。不要贴到公开 Issue、日志、群聊或源码。它不包含管理员密码、支付宝应用私钥、GitHub Token、其他平台密钥或全账号凭据。

通用 Skill 可在登录后复制或下载：`GET /api/admin/skill`、`GET /api/admin/skill.zip`。拿到复制任务的 AI 也可使用临时 Bearer 授权请求 `GET /api/integration/v1/skill.zip`，解压到任务临时目录使用；不需要管理员 Cookie、额外全局账号授权或自动安装全局 Skill。令牌放在 Authorization 请求头，不能放入 URL/query。

复制任务与 ZIP 均包含付款后客户端同步要求，以及无密钥的 `payment-completion.mjs` 模板：等待实际权益、focus/resume 刷新、账号切换清理和超时恢复。中心已正式开放、目标平台启用且签名目录允许收款时，产品 AI 可在其已授权项目内完成部署并开放购买入口，不必回到支付仓库重复改总开关。单平台授权仍不能改商户或总开关；真实付款由用户人工完成。配置应用、产品后端/网页部署、安装包发布和实际开通必须分别核实。

## 授权如何限制操作

- 每次授权绑定一个 `clientId`，`mode=create` 表示新建，`mode=update` 表示修改已存在平台；它与 `paymentMode=live/sandbox` 是不同概念。
- 管理页面签发的授权有效期为 2 小时，不能凭令牌扩大目标、延长有效期或访问别的平台。服务端保存令牌哈希，原始令牌仅在生成任务时交付。
- `domainMode=fixed` 的新增或修改 webhook/返回来源必须处于授权范围；更新可保留未改动的原地址。`domainMode=auto` 允许 AI 为该产品加入必要合法公网 HTTPS 来源，plan 显示 `addedOrigins`，apply 时纳入授权记录并写入审计；初始最多 50 个，累计最多 100 个。旧授权缺省 fixed。
- 两种域名模式都允许 AI 在来源下设计具体路径。自动模式不授予其他平台、产品仓库、DNS 或域名购买权限；后台平台配置可查看实际 webhook 和返回来源，授权列表展示签发模式及已纳入来源。
- 新平台应用成功后，才生成该平台长期 API/webhook 凭证。更新平台保留原凭证，不通过配置计划旋转密钥。
- 授权撤销或过期后，context、Skill 下载、plan、apply 等后续授权请求均不能继续。已完成的配置不会自动回滚，已经交付给产品后端的长期凭证也不会因短期授权撤销而失效。

管理页面的“清除显示”仅清理当前任务文本，不等于撤销授权；使用“短期授权”列表中的撤销操作才会使服务端授权失效。

## 配置版本与计划应用

`GET /api/integration/v1/context` 返回目标平台视图、`client.version`、`allowedOrigins`、`domainMode`、`pricingMode`、操作类型和实际支付环境。新平台 `client=null`，版本使用 `absent`。返回的 `credentials` 只属于目标平台；通用 CLI 默认隐藏它们。

`POST /api/integration/v1/plan` 接收完整的目标 `config` 与 `expectedVersion`，返回 `planId`、`before`、`after`、`baseVersion`、`addedOrigins` 和到期时间。计划最多保留 15 分钟，且不能超出授权有效期。`POST /api/integration/v1/apply` 使用同一授权提交 `{planId}`，再次核对目标、域名模式和配置版本后应用。

这是按单个平台进行的版本比较更新：新平台要求 `absent`，已有平台要求读取时的 SHA-256 版本。若另一个任务已经修改同一平台，返回 409；重新读取并核对差异，不能强行覆盖。修改其他平台不应导致当前平台被整表替换。重复提交已成功应用的同一计划返回原结果。

手动配置也先预览，再保存目标平台与其读取时的版本。已有平台 ID 保持不变，更新保存原 API/webhook Secret；其他平台、历史订单与付款事件保持独立。

改价影响之后创建的订单，历史订单保存的金额不会改变。修改 webhook 会影响尚未成功投递的通知，应先让新接收端就绪并安排旧端过渡。停止平台会阻止新订单和新发起付款，已有付款通知、查单及重试仍须处理。不要删除历史订单或待投递事件来“清理”配置。

## 商品和价格维护

在已有平台的编辑页面维护 SKU、商品名称、人民币金额、启用状态、商品说明和权益/有效期说明。金额用两位小数；SKU 是产品后端使用的固定标识。停售优先关闭商品启用状态，以保留可核对的商品记录；停售不取消已创建订单或已购买权益。

商品配置示例：

```json
{"subject":"月度套餐","amount":"9.90","enabled":true,"description":"商品介绍","entitlement":"购买后有效 30 天，具体额度按产品规则"}
```

保存前先看差异，平台版本冲突时重新读取，不强制覆盖。后台只维护支付目录与权益说明，产品后端负责实际开通逻辑。已实现签名目录读取（`GET /api/v1/catalog`）的产品会读取新价；未改造的旧产品需要先让项目 AI 实现目录展示/下单校验，不能声称保存后自动同步。权益说明是文案，真实权益规则修改仍需产品同步。目录不缓存或采用明确短缓存；目录与下单之间改价时，产品应让用户确认新报价后以新业务订单重建。历史通知按该笔业务订单创建时的金额和权益快照处理，不能用最新套餐覆盖旧承诺。

## 订单手动管理

在“订单记录”打开单笔订单，可查看当前付款期限、各次支付尝试、支付宝交易号、最近操作审计和额外付款记录。普通列表和打开详情都是只读操作，不会向支付宝发起查询或持续提交 GitHub。

- **提前关闭**：仅用于未付款订单。先向支付宝验签查单，已付则直接确认付款；已有未付交易先调用上游关单，再关闭中心付款入口并移出待查队列。不能把已付款订单关成未付，也不执行退款或撤销已开通权益。
- **重新启用**：仅用于已关闭且仍未付的订单。先核实历史支付尝试，确认没有真实付款和未消除的旧链接付款窗口后，为同一订单新建一次支付尝试，重新给予 10 分钟付款期限。原业务订单号、中心订单 ID、创建时间、初始到期时间、金额、SKU、标题和权益依据均保留；当前平台、商品及总收款开关必须仍允许付款。操作返回的收银台链接可重新交给该用户，普通产品 API 重试不会自行重开订单。
- **核实付款并补记**：可核查待付、已关闭或已付订单的历史尝试。只有支付宝已验签查询确认成功且金额、收款账户、订单与环境匹配时，才补记为已付，并按原事件进行通知和幂等履约。交易不存在或仍待付时保持原状态；支付宝确认已关闭可同步关闭原待付订单，已关闭订单不会因此重新进入周期查单。不能凭截图、回跳或管理员判断直接标记已付款。

操作前填写原因并确认；后台使用管理员当前会话记录操作者。每次操作带上详情返回的订单版本和唯一请求 ID；页面重试复用同一请求 ID，不重复关单、重开或创建付款事件。遇到版本冲突，应重新读取订单和审计，核对并发付款或其他管理员操作后再决定。成功变更、工作队列、报表与操作审计在同一 Git 事务保存。

**提前关闭不保证撤销尚未在支付宝创建交易的旧签名链接。** 查询确认交易不存在时，支付宝没有可关闭的交易；中心会停止继续签发，但已发出的链接可能在原 `time_expire` 前仍能付款。详情显示 `mayStillPayUntil` 和未取得上游关闭确认的提示；这段时间内拒绝重新启用，避免同一购买存在两个可付尝试。需要时用“核实付款并补记”复核。到期任务不会因关闭后的核查而恢复持续查单。

重新启用会分配新的支付宝商户单号，不会复活已经关闭的支付宝交易。旧尝试的关闭通知不能关闭新尝试；任一历史尝试的真实付款仍归到原中心订单。若不同尝试都已实付，额外交易记入详情的 `duplicatePayments` 并醒目提示人工核对处理；每笔独立真实收款按各自上海付款日期计入已确认付款总额和笔数，不能漏算。原订单金额快照及单次权益通知不变，不重复开通，也不自动退款。统计仍不是净结算或退款后净收入。

原单确认已付款后，其他已发出的未付尝试还须收尾。详情用 `cleanupPending` 和可能的 `mayStillPayUntil` 提示风险；“核实付款并补记”会尝试关闭其余待付交易，后台也将该已付订单保留在持久队列中重试。其他尝试查单或关单失败不撤销已经核实的付款、通知或审计成功结果。尚未创建交易的旧链接须等实际签发期限结束，再确认交易不存在，或取得上游关闭确认后才完成收尾。收尾重试不预写查单时间，结果没有变化时不会持续产生仅更新时间戳的 GitHub 提交。

报表投影的 `expiresAt` 保留原初始到期快照；单笔操作详情和产品查单响应的 `expiresAt` 返回当前活跃尝试期限。重新启用后的付款截止以单笔最新详情为准。每单最多保留 20 次支付尝试，达到上限时使用新的业务订单购买。

管理员重新启用后，已经因 `CLOSED` 停止等待的旧客户端不会自动恢复；让用户重新打开本次收银台链接或在产品中手动刷新原订单。重新启用只恢复原购买的付款机会，不能用当前新价或新权益覆盖原购买承诺。

管理接口均要求有效管理员会话；写接口另须同源 Origin 和 CSRF：

| 接口 | 请求与响应 |
| --- | --- |
| `GET /api/admin/orders/:id` | 返回脱敏 `order`、`version`、可用 `actions` 和最近 20 条 `audit`，不返回产品/商户凭证或原返回 URL |
| `POST /api/admin/orders/:id/close` | JSON `{expectedVersion,requestId,reason}`，核实并提前关闭 |
| `POST /api/admin/orders/:id/reopen` | 相同请求结构，核实后新建付款尝试；成功时顶层返回 `checkoutUrl` |
| `POST /api/admin/orders/:id/reconcile` | 相同请求结构，向支付宝核实并补记真实付款 |

## 管理员与加密存储配置

以下是默认 Secret 初始化或明确恢复 Secret 类型时的流程，邮箱和密码由本机交互终端输入，不写进命令历史或明文 JSON 文件。**第二条 `secret bulk` 命令会把这 5 项恢复为 Secret 类型，不是当前 Text 维护约定下的日常发布步骤。** 现有 Worker 按 [环境变量说明](environment-variables.md) 维护；修改密码时只更新脚本生成的新哈希及确需变更字段，其他原值和 Text 类型保持不变。

```sh
python3 -c 'import getpass,json,sys; print("管理员邮箱：",file=sys.stderr); email=input().strip(); password=getpass.getpass("管理员密码："); json.dump({"email":email,"password":password},sys.stdout)' | node scripts/configure-admin.mjs
npx wrangler secret bulk secrets/admin-worker-secrets.json
```

脚本从标准输入接收 `{email,password}`，密码要求 12–1024 个字符。密码经带 pepper 的 PBKDF2 派生，**明文密码不落盘**；输出仅说明准备完成。被 Git 忽略的 `secrets/admin-worker-secrets.json` 权限为 0600，包含账户邮箱、密码哈希、pepper、会话签名密钥和注册表加密密钥。该文件仍是敏感备份，不能打印或提交。

原 5 项敏感运行变量：`ADMIN_EMAIL`、`ADMIN_PASSWORD_HASH`、`ADMIN_PASSWORD_PEPPER`、`ADMIN_SESSION_SECRET`、`REGISTRY_ENCRYPTION_KEY`。脚本仅在本机对应原字段存在且非空时复用 pepper、会话密钥和注册表加密密钥；字段缺失或为空会生成新值，即使配置文件本身存在也一样。维护现有服务前必须先恢复完整原配置，尤其已有加密注册表时不能上传新生成的加密 key。原 key 齐全且邮箱不变时，修改密码只更新盐及派生哈希。新密码哈希部署后，旧登录会话因凭证指纹不符而失效。

登录使用 Secure、HttpOnly、SameSite=Strict 的主机 Cookie，会话有效期为 8 小时；管理写操作校验同源 Origin 和 CSRF Token。登录与临时接入 API 的限流绑定需随 Worker 配置部署。页面不内置管理员账户或密码。

平台目录、平台长期凭证、授权哈希、计划与接入配置审计记录使用 AES-256-GCM 加密后写入私有 GitHub 数据仓库的 `system/clients.enc.json`。`REGISTRY_ENCRYPTION_KEY` 只保留在本机安全备份及 Cloudflare 服务端配置，按用户 2026-10-18 的 [Text 维护约定](environment-variables.md) 保留原值，不能放进该数据仓库或代码仓库。这里加密的是接入注册表；订单、订单操作审计和 outbox 仍按原架构保存为私有账本 JSON，并非所有 GitHub 文件都经过此加密。

**加密密钥必须保留。** 已有加密注册表时，不要用新生成的随机 key 覆盖旧 key。若本机配置文件丢失，先从安全备份恢复原 key，再运行配置流程；不能靠重新生成密钥恢复旧数据。

仅当 `system/clients.enc.json` 不存在时，服务才读取旧 `CLIENTS_JSON` 作为初始化基线。第一次保存注册表后，加密数据成为权威来源；再修改 legacy 配置不会覆盖后台配置。加密数据存在但格式错误、损坏、缺少 key 或无法解密时必须报错，**禁止退回旧配置继续运行**，否则会重新启用旧商品或旧凭证。

## 接入与验证边界

管理配置和 Skill 只负责支付中心侧登记及指导产品代码接入。产品自己的登录认证、订单归属、原始请求体验签、金额核对、数据库事务去重和权益开通仍由产品后端实现。长期凭证只能进入该后端的 Secret；通用 CLI 仅在明确指定 `--credentials-file` 时，独占写入 Git 忽略的新 0600 文件。

本次最终验证结果见 [交付状态](status.md)。应用上线、真实小额付款、支付宝到账和实际产品权益落库必须分别取得证据；管理后台保存成功不能代替这些验收。
